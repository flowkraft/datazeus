## The situation this lesson prepares you for

Someone gives you access to a database and asks you to "have a look at the products". You open it and see a list of table names. That is all you have.

Two commands get you from there to understanding the data:

- `SELECT *` — asks for **every column**: to see what a table holds.
- `SELECT "Col1", "Col2"` — asks for **only those columns**: to read the data.

You will also learn to read what type each column is, because that explains results that otherwise look wrong.

Every query below runs on the Northwind sample database that ships with DataPallas.

## Ask a table for everything

`SELECT *` means "give me every column". Start with a small table:

```sql
SELECT *
FROM "Categories";
```

| CategoryID | CategoryName | Description |
| ---------: | ------------ | ----------- |
| 1 | Beverages | Soft drinks, coffees, teas, beers, and ales |
| 2 | Condiments | Sweet and savory sauces, relishes, spreads, and seasonings |
| 3 | Confections | Desserts, candies, and sweet breads |
| 4 | Dairy Products | Cheeses |
| 5 | Grains/Cereals | Breads, crackers, pasta, and cereal |
| 6 | Meat/Poultry | Prepared meats |
| 7 | Produce | Dried fruit and bean curd |
| 8 | Seafood | Seaweed and fish |

Type it into CloudBeaver yourself and hit Run — resist the copy-paste, typing is part of how it sticks. You should get this:

That is the entire table: eight rows, three columns. Nothing is hidden, and now you know what this business means by a "category".

Three words for what you are looking at, because you will use them constantly:

- A **table** holds all the records of one kind. `"Categories"` holds every category.
- A **column** is one named piece of information that every row carries. `CategoryName` holds each category's name.
- A **row** is one complete record. Row 1 is the Beverages category — its id, its name and its description together.

## The same query on a wider table

`SELECT *` works on any table. Run it on the staff:

```sql
SELECT *
FROM "Employees";
```

Every row comes back with **eighteen columns**: `EmployeeID`, `LastName`, `FirstName`, `Title`, `TitleOfCourtesy`, `BirthDate`, `HireDate`, `Address`, `City`, `Region`, `PostalCode`, `Country`, `HomePhone`, `Extension`, `Photo`, `Notes`, `ReportsTo`, `PhotoPath`.

You asked who works here. The database handed back everything it stores about each person. This is the normal experience with real tables, and it is the reason for the second command.

### The cost is not only on screen

Unreadable output is the part you notice. There is a second cost you do not see:

- The database **reads** every column you asked for, including the ones you ignore.
- All of them are **serialized and sent over the network** to whatever asked — your application, your BI tool, your script.
- Wide columns are the expensive ones. `Notes` and `Photo` here can hold a lot of text, and `SELECT *` ships them whether or not you look at them.

On a three-row table you will never notice. On a wide table with millions of rows, inside an application that runs the query thousands of times a day, the columns nobody needed are a measurable share of the time users spend waiting.

So here is the rule worth remembering: use `SELECT *` to **discover which columns a table has**. Once you know them, **name the columns you want** — that is how you read the data itself.

## Ask for only the columns you want

Instead of `*`, list the columns you actually need, separated by commas:

```sql
SELECT "FirstName", "LastName", "Title"
FROM "Employees";
```

| FirstName | LastName | Title |
| --------- | -------- | ----- |
| Nancy | Davolio | Sales Representative |
| Andrew | Fuller | Vice President, Sales |
| Janet | Leverling | Sales Representative |

Three columns instead of eighteen. That list between `SELECT` and `FROM` is called the **select list**, and choosing what goes in it is most of what writing a query is.

Remember the double quotes around each column name: they tell the database to take the name exactly as you typed it. That is the rule from the previous lesson, and it applies to every query you write against this database.

## The select list also decides the column order

Look carefully at the result above, then at the table's own structure: `"Employees"` stores `LastName` **before** `FirstName`. The result shows `FirstName` first.

The database did not reorder anything. You asked for `"FirstName"` first, so it came back first. The order of the columns in your answer is entirely your choice — swap the two names in the query and the two columns swap in the output.

## Limiting the rows

The select list controls the columns. A separate keyword, `LIMIT`, controls how many rows come back. `"Products"` holds twenty rows; this asks for five of them:

```sql
SELECT "ProductName", "UnitPrice"
FROM "Products"
LIMIT 5;
```

| ProductName | UnitPrice |
| ----------- | --------: |
| Chai | 18.0000 |
| Chang | 19.0000 |
| Aniseed Syrup | 10.0000 |
| Chef Antons Cajun Seasoning | 22.0000 |
| Scottish Longbreads | 12.5000 |

Use `LIMIT` whenever you are exploring an unfamiliar table. It costs nothing and protects you from asking a ten-million-row table to print itself.

Two separate controls, then: **the select list chooses the columns**, and **`LIMIT` chooses the rows**.

## Why the price shows as 18.0000

Chai costs eighteen. The result says `18.0000` — four decimal places on a round number.

Nothing is wrong with the data. That is the column's **data type** being displayed. Every column is declared to hold a particular kind of value: whole numbers, decimal numbers with a fixed number of decimal places, text, dates. `UnitPrice` was declared as a decimal with four decimal places, so all four are printed even when they are zeros.

Types matter beyond appearance. They decide what values a column will accept, how it sorts, and whether you can do arithmetic on it. You cannot multiply text, and a whole-number column will not store `12.5`.

### Showing two decimals instead

Four decimal places on a price looks wrong in front of another person. `ROUND` changes how a value is displayed:

```sql
SELECT "ProductName", ROUND("UnitPrice", 2)
FROM "Products"
LIMIT 5;
```

| ProductName | round(UnitPrice, 2) |
| ----------- | ------------------: |
| Chai | 18.00 |
| Chang | 19.00 |
| Aniseed Syrup | 10.00 |
| Chef Antons Cajun Seasoning | 22.00 |
| Scottish Longbreads | 12.50 |

The stored data is untouched — `UnitPrice` still holds four decimal places, and the next query that reads it plainly will show `18.0000` again. You changed this one answer, not the table.

Notice the column heading. You did not name that column, so the engine invented a name for it — and each engine invents a different one: DuckDB calls it `round(UnitPrice, 2)`, PostgreSQL calls it just `round`. Naming it yourself is called an **alias**, and it gets its own lesson shortly.

## Ask the database what its types are

You do not have to guess. Every standard database keeps a set of tables describing its own tables, and you query them like any other table:

```sql
SELECT column_name, data_type
FROM information_schema.columns
WHERE table_name = 'Products'
ORDER BY ordinal_position;
```

| column_name | data_type |
| ----------- | --------- |
| ProductID | INTEGER |
| ProductName | VARCHAR |
| SupplierID | INTEGER |
| CategoryID | INTEGER |
| QuantityPerUnit | VARCHAR |
| UnitPrice | DECIMAL(10,4) |
| UnitsInStock | SMALLINT |
| UnitsOnOrder | SMALLINT |
| ReorderLevel | SMALLINT |
| Discontinued | SMALLINT |

Ten rows, one for each column in `"Products"`. `UnitPrice` is `DECIMAL(10,4)` — up to ten digits in total, four of them after the decimal point. That is where the trailing zeros come from.

Two keywords in that query belong to later lessons and are used here only to get a tidy result: `WHERE` selects which rows you keep, and `ORDER BY` sorts them.

## Type names differ between databases

Run that same catalog query against the Northwind on PostgreSQL rather than DuckDB and the type names change:

| column | DuckDB reports | PostgreSQL reports |
| ------ | -------------- | ------------------ |
| UnitPrice | `DECIMAL(10,4)` | `numeric` |
| ProductName | `VARCHAR` | `text` |
| UnitsInStock | `SMALLINT` | `integer` |

The data is identical. Only the vocabulary differs. Each database has its own names for the same small set of ideas: whole numbers, decimals, text, dates, true/false.

This is worth seeing now so that the first time you move a query between two databases you recognise it as a naming difference rather than a mistake in your query.

## Two kinds of quotes

One last detail from that catalog query, and it has nothing to do with types — the two kinds of quotes:

- `'Products'` in **single** quotes is a text **value**, compared against the contents of a column.
- `"ProductName"` in **double** quotes is the **name of a column**.

They are not interchangeable, and putting a column name in single quotes is among the most common errors beginners make.

## What you can do now

Given any table in any database:

1. `SELECT * FROM "TheTable" LIMIT 5;` to see what it holds.
2. `SELECT "the", "columns", "you", "want" FROM "TheTable";` to read the data you actually need.
3. Query `information_schema.columns` when a value looks unexpected.
