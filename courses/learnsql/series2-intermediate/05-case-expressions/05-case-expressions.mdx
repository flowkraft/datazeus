## Light, medium or heavy?

The shipping team is reviewing freight costs, and they want **every order labelled light, medium or heavy**: freight under 25 is light, under 60 is medium, and anything more is heavy.

With Series 1 alone, this takes three queries, one `WHERE` per band, and the three answers put together by hand. Even then the result is three counts, not a label on each order. This lesson adds the tool that does it in one query: **CASE**, SQL's if-then.

Every query below runs on Northwind Company, the dataset installed in the <a href="/academy/learn-sql/subqueries" target="_blank" rel="noopener" className="font-medium underline underline-offset-4">first lesson of this series</a>, and assumes `SET search_path TO northwind_co_s;` has been run in the CloudBeaver editor. Write each query and compare the result with the table under it.

## CASE: a value chosen row by row

{/* The same highlight as the video: the three branch lines, in grey. */}

```sql file=./scripts/freight-band-per-order.sql {3-5}
SELECT "OrderID", "Freight",
       CASE
         WHEN "Freight" < 25 THEN 'light'
         WHEN "Freight" < 60 THEN 'medium'
         ELSE 'heavy'
       END AS "Band"
FROM "Orders"
ORDER BY "OrderID"
LIMIT 6;
```

For every row, CASE checks each `WHEN` **from the top**. The first test that is true gives the row its value, and CASE stops there. If no test is true, the `ELSE` value is used. `END` closes the CASE, and `AS "Band"` names the new column.

It is an expression, like the calculated columns from the <a href="/academy/learn-sql/distinct-aliases-expressions" target="_blank" rel="noopener" className="font-medium underline underline-offset-4">aliases and expressions lesson</a>. The difference is that it chooses its value instead of calculating it.

## Count the bands

The new column can be grouped like any other. Use the same CASE with `GROUP BY "Band"`:

{/* The same highlight as the video: the GROUP BY line, in grey. */}

```sql file=./scripts/orders-per-band.sql {8}
SELECT CASE
         WHEN "Freight" < 25 THEN 'light'
         WHEN "Freight" < 60 THEN 'medium'
         ELSE 'heavy'
       END AS "Band",
       count(*) AS "Orders"
FROM "Orders"
GROUP BY "Band"
ORDER BY min("Freight");
```

| Band   | Orders |
| ------ | ------ |
| light  | 2446   |
| medium | 4156   |
| heavy  | 3398   |

2446, 4156 and 3398 add up to 10000, every order in the table. The label the query made up is the thing it groups by. `ORDER BY min("Freight")` sorts the bands by the smallest freight in each, so light comes first instead of in alphabetical order.

PostgreSQL and DuckDB both let `GROUP BY` use the name `"Band"` from the `SELECT`. Some databases do not, and there you repeat the whole CASE in the `GROUP BY`.

## The first true WHEN wins

Now swap the first two `WHEN` lines, so medium is tested before light:

{/* The same highlight as the video: the two swapped lines, in red. */}

```sql file=./scripts/orders-per-band-whens-swapped.sql {2-3}#err
SELECT CASE
         WHEN "Freight" < 60 THEN 'medium'
         WHEN "Freight" < 25 THEN 'light'
         ELSE 'heavy'
       END AS "Band",
       count(*) AS "Orders"
FROM "Orders"
GROUP BY "Band"
ORDER BY min("Freight");
```

There are no light orders at all, and medium went from 4156 to 6602, which is 2446 + 4156. The 2446 light orders are still in the table, and their freight did not change. What changed is the order of the tests: **under 25 is also under 60**. The first `WHEN` now asks "under 60?", every light order answers yes, and CASE stops there. The light test is never reached.

There is no error and no warning. The result simply has one band fewer. So **write the narrow tests first**: a wide test above a narrow one catches its rows before the narrow one is checked.

## No ELSE means NULL

Finance only cares about heavy orders, freight over 50. So the CASE gets one `WHEN` and no `ELSE`:

{/* The same highlight as the video: the CASE's one WHEN, in grey. */}

```sql file=./scripts/heavy-label-no-else.sql {2-3}
SELECT CASE
         WHEN "Freight" > 50 THEN 'heavy'
       END AS "Label",
       count(*) AS "Orders"
FROM "Orders"
GROUP BY "Label"
ORDER BY "Label" NULLS LAST;
```

{/* The same highlight as the video: the NULL row in terracotta. */}

<div className="[&_tbody_tr:nth-child(2)]:bg-[rgb(var(--hl-fault)/var(--hl-row))] [&_tbody_tr:nth-child(2)_td]:font-bold [&_tbody_tr:nth-child(2)_td]:text-[rgb(var(--hl-fault-ink))]">

| Label    | Orders |
| -------- | ------ |
| heavy    | 4383   |
| `[NULL]` | 5617   |

4383 orders are heavy, and **5617 orders are labelled NULL**, more than half of them. A CASE with no `ELSE` returns NULL for every row that no `WHEN` matched. It does not look harmful here, because the 5617 are still counted. The trouble starts when a query tests the label.

### How many orders are not heavy?

The label is made in a subquery in `FROM` (the <a href="/academy/learn-sql/subqueries" target="_blank" rel="noopener" className="font-medium underline underline-offset-4">subqueries lesson</a>), because a `WHERE` cannot see a name given in the same query's `SELECT`. Then the `WHERE` keeps the orders whose label is not 'heavy':

{/* The same highlight as the video: the WHERE, in red. */}

```sql file=./scripts/not-heavy-no-else.sql {7}#err
SELECT count(*) AS "Not heavy"
FROM (SELECT CASE
               WHEN "Freight" > 50
               THEN 'heavy'
             END AS "Label"
      FROM "Orders") AS t
WHERE "Label" <> 'heavy';
```

| Not heavy |
| --------- |
| 0         |

Zero, although 5617 orders are not heavy. Every one of them is labelled NULL, and this is the rule from the <a href="/academy/learn-sql/null-and-three-valued-logic" target="_blank" rel="noopener" className="font-medium underline underline-offset-4">NULL lesson</a>: NULL is not unequal to 'heavy'. The comparison `NULL <> 'heavy'` is **unknown**, and `WHERE` keeps only rows where the test is true. All 5617 are dropped.

### Write the ELSE

Give every other order a real label:

{/* The same highlight as the video: the ELSE line, in green. */}

```sql file=./scripts/not-heavy-with-else.sql {5}#good
SELECT count(*) AS "Not heavy"
FROM (SELECT CASE
               WHEN "Freight" > 50
               THEN 'heavy'
               ELSE 'standard'
             END AS "Label"
      FROM "Orders") AS t
WHERE "Label" <> 'heavy';
```

| Not heavy |
| --------- |
| 5617      |

One line, and the 5617 orders are back.

## The short form

When every `WHEN` compares the same column with a value, the column can be written once, after `CASE`. Here it turns the courier number in `"ShipVia"` into a name, written from memory with the three couriers Series 1's Northwind had:

{/* The same highlight as the video: CASE "ShipVia" and its first WHEN, in grey. */}

```sql file=./scripts/shipper-names-by-case.sql {1-2}
SELECT CASE "ShipVia"
         WHEN 1 THEN 'Speedy Express'
         WHEN 2 THEN 'United Package'
         WHEN 3 THEN 'Federal Shipping'
       END AS "Shipper",
       count(*) AS "Orders"
FROM "Orders"
GROUP BY "Shipper"
ORDER BY "Shipper";
```

511 orders have no courier name. Northwind Company has a fourth courier, Northern Freight Lines, with `"ShipVia"` 4. The CASE does not name it and has no `ELSE`, so its orders get NULL: the missing `ELSE` again, arriving the way it usually does at work, through a list typed into a query that went out of date.

The names are already stored in the `"Shippers"` table, and a join reads them from there:

```sql file=./scripts/shipper-names-by-join.sql
SELECT s."CompanyName" AS "Shipper",
       count(*) AS "Orders"
FROM "Orders" o
JOIN "Shippers" s
  ON s."ShipperID" = o."ShipVia"
GROUP BY s."CompanyName"
ORDER BY s."CompanyName";
```

| Shipper                | Orders |
| ---------------------- | ------ |
| Federal Shipping       | 831    |
| Northern Freight Lines | 511    |
| Speedy Express         | 7513   |
| United Package         | 1145   |

All four couriers, by the names the company stores. The join is better here: when a courier is added or renamed, the table changes and the query does not have to. **CASE is for labels that nobody stored**, such as light, medium and heavy. If the label already lives in a table, read it from the table.

## COALESCE is a CASE

The <a href="/academy/learn-sql/null-and-three-valued-logic" target="_blank" rel="noopener" className="font-medium underline underline-offset-4">NULL lesson</a> used `COALESCE` to put a stand-in where a value is missing. It is a short way of writing a CASE: when the value is NULL, use the stand-in; otherwise use the value. Customers in Canada have a province in `"Region"`, and customers in Poland have none, so these rows take both branches:

{/* The same highlight as the video: COALESCE and the CASE's three lines, in grey. */}

```sql file=./scripts/region-coalesce-and-case.sql {2,4-6}
SELECT "CompanyName", "Country",
       COALESCE("Region", '(none)')
         AS "With COALESCE",
       CASE
         WHEN "Region" IS NULL THEN '(none)'
         ELSE "Region"
       END AS "With CASE"
FROM "Customers"
WHERE "Country" IN ('Canada', 'Poland')
ORDER BY "CustomerID";
```

| CompanyName        | Country | With COALESCE | With CASE |
| ------------------ | ------- | ------------- | --------- |
| Cedar Grocers      | Poland  | (none)        | (none)    |
| Emerald Fine Foods | Canada  | BC            | BC        |
| Golden Supermarket | Canada  | BC            | BC        |
| Kestrel Provisions | Poland  | (none)        | (none)    |
| Pampas Foods       | Canada  | BC            | BC        |
| Tundra Foods       | Canada  | QC            | QC        |
| Upland Trading     | Canada  | QC            | QC        |
| Zenith Food Hall   | Poland  | (none)        | (none)    |

The two columns are identical, and they stay identical for all 120 customers.

## CASE inside SUM: a column for each status

Every order also has a `"Status"`: Shipped, Cancelled or Open. A manager wants, for every channel, **how many orders there are and how many are in each status**, side by side, one row per channel.

That is three counts with three different conditions, and one query has only one `WHERE`. The way around it is to move each condition into its own column:

{/* The same highlight as the video: the SUM(CASE …) lines, in grey. */}

```sql file=./scripts/status-per-channel.sql {3-8}
SELECT "Channel",
       count(*) AS "Orders",
       SUM(CASE WHEN "Status" = 'Shipped'
           THEN 1 ELSE 0 END) AS "Shipped",
       SUM(CASE WHEN "Status" = 'Cancelled'
           THEN 1 ELSE 0 END) AS "Cancelled",
       SUM(CASE WHEN "Status" = 'Open'
           THEN 1 ELSE 0 END) AS "Open"
FROM "Orders"
GROUP BY "Channel"
ORDER BY "Orders" DESC;
```

| Channel   | Orders | Shipped | Cancelled | Open |

| Web       | 2765   | 2669    | 50        | 46   |

Sales rep has 3749 orders: 3669 shipped, 61 cancelled and 19 open. `SUM` adds numbers, so how did it count? Each CASE turns every order in its status into a 1 and every other order into a 0, and `SUM` adds the ones. The result is a count, **without a `WHERE`**, next to the count of all orders. The three status columns add back up to the orders on every row, which is a quick check that no status was missed.

You can add as many of these columns as you need, one per status, all in the same `GROUP BY`. This is how a report with a column for each status is built.

### The same, with count

You will also see it written with `count`, and there the missing `ELSE` is on purpose:

{/* The same highlight as the video: the count(CASE …) lines, in green. */}

```sql file=./scripts/status-per-channel-counted-with-count.sql {3-8}#good
SELECT "Channel",
       count(*) AS "Orders",
       count(CASE WHEN "Status" = 'Shipped'
             THEN 1 END) AS "Shipped",
       count(CASE WHEN "Status" = 'Cancelled'
             THEN 1 END) AS "Cancelled",
       count(CASE WHEN "Status" = 'Open'
             THEN 1 END) AS "Open"
FROM "Orders"
GROUP BY "Channel"
ORDER BY "Orders" DESC;
```

Every order outside the status gets NULL, `count` of a column skips NULLs, and the result is the same table: Sales rep still has 61 cancelled. In the filter above, the missing `ELSE` was a bug. Here it does the counting. The difference is whether you meant the NULLs.

## A share that comes back as 0

Sales rep has the most cancelled orders. It also has by far the most orders, so 61 on its own says little. The fair comparison is **the share**: the cancelled count divided by all of that channel's orders. Add it as a fourth column:

{/* The same highlight as the video: the division, in grey. Nothing on the card looks wrong yet. */}

```sql file=./scripts/cancelled-share-per-channel-integer-division.sql {5-6}
SELECT "Channel",
       count(*) AS "Orders",
       SUM(CASE WHEN "Status" = 'Cancelled'
           THEN 1 ELSE 0 END) AS "Cancelled",
       SUM(CASE WHEN "Status" = 'Cancelled'
           THEN 1 ELSE 0 END) / count(*) AS "Share"
FROM "Orders"
GROUP BY "Channel"
ORDER BY "Orders" DESC;
```

This is what CloudBeaver shows:

**Every share is 0**, on a row that says 61 cancelled right next to it. There is no error. On PostgreSQL, **a whole number divided by a whole number is a whole number**: `SUM` of ones and zeros is a whole number, `count(*)` is a whole number, so 61 ÷ 3749 is worked out as 0.016… and the fraction is thrown away. Every channel has fewer cancelled orders than orders, so every channel gets 0.

<Callout>
**The engines disagree here, and the koans run on the other one.** Run the same query in DuckDB and Sales rep's share is **0.01627…**: DuckDB's `/` always keeps the fraction. PostgreSQL, SQL Server and SQLite throw it away when both sides are whole numbers; MySQL and DuckDB keep it. So a share that looks right in one tool can be a column of zeros in the next. **Write it so that it cannot depend on the engine**: put a decimal number into the calculation before the division, as below.
</Callout>

### Multiply by 100.0 first

{/* The same highlight as the video: the ROUND(100.0 * …) lines, in green. */}

```sql file=./scripts/cancelled-share-per-channel.sql {5-6}#good
SELECT "Channel",
       count(*) AS "Orders",
       SUM(CASE WHEN "Status" = 'Cancelled'
           THEN 1 ELSE 0 END) AS "Cancelled",
       ROUND(100.0 * SUM(CASE WHEN "Status" = 'Cancelled'
             THEN 1 ELSE 0 END) / count(*), 1) AS "Cancelled %"
FROM "Orders"
GROUP BY "Channel"
ORDER BY "Orders" DESC;
```

`100.0` has a decimal point, so `100.0 * SUM(…)` is a decimal number, and a decimal divided by a whole number keeps its fraction on every database. The 100 turns the share into a percentage, and `ROUND(…, 1)` keeps one decimal place. The order matters: `100.0 * SUM(…) / count(*)` multiplies first. Writing `100 * SUM(…) / count(*)` without the `.0` gives PostgreSQL 1 for Sales rep instead of 1.6, and `SUM(…) / count(*) * 100.0` divides first and gives 0 again.

### A share travels with its count

The count and the share point at opposite ends of the table. Sales rep has **the most** cancelled orders and **the lowest** share, 1.6. EDI has **the fewest**, 22, and **the highest** share, 2.2. It is tempting to read that as "EDI is where orders get cancelled".

First compare it with the whole company. The same columns without a `GROUP BY` give one row for all the orders:

```sql file=./scripts/cancelled-share-company.sql
SELECT count(*) AS "Orders",
       SUM(CASE WHEN "Status" = 'Cancelled'
           THEN 1 ELSE 0 END) AS "Cancelled",
       ROUND(100.0 * SUM(CASE WHEN "Status" = 'Cancelled'
             THEN 1 ELSE 0 END) / count(*), 1) AS "Cancelled %"
FROM "Orders";
```

| Orders | Cancelled | Cancelled % |
| ------ | --------- | ----------- |
| 10000  | 175       | 1.8         |

1.8 for the company. EDI's 2.2 is above it, but by very little: it is 22 orders of 1001, and **with four fewer cancellations EDI would read 1.8**, the company's own share. Every channel sits close to the company's figure. A share on its own hides how few rows are behind a difference, which is why a report prints the count beside every share.

## Case file: one courier stands out

This series follows one case through Northwind Company. The <a href="/academy/learn-sql/subqueries" target="_blank" rel="noopener" className="font-medium underline underline-offset-4">subqueries lesson</a> ended on a question: in 2024, orders grew while invoicing fell. Why? An order is invoiced once its ship date is recorded, so one place to look is **the orders marked Shipped that have no `"ShippedDate"`**. The report is this lesson's shape: per courier, all of its 2024 orders, how many of them are marked shipped with no ship date, and the share, beside its count. The one new thing is a `WHEN` with two tests joined by `AND`:

{/* The same highlight as the video: the two SUM(CASE …) columns, in grey. */}

```sql file=./scripts/shipped-no-ship-date-per-courier-2024.sql {3-6}
SELECT s."CompanyName" AS "Courier",
       count(*) AS "Orders",
       SUM(CASE WHEN o."Status" = 'Shipped' AND o."ShippedDate" IS NULL
           THEN 1 ELSE 0 END) AS "Shipped, no date",
       ROUND(100.0 * SUM(CASE WHEN o."Status" = 'Shipped' AND o."ShippedDate" IS NULL
             THEN 1 ELSE 0 END) / count(*), 1) AS "Share %"
FROM "Orders" o
JOIN "Shippers" s ON s."ShipperID" = o."ShipVia"
WHERE o."OrderDate" >= DATE '2024-01-01'
  AND o."OrderDate" < DATE '2025-01-01'
GROUP BY s."CompanyName"
ORDER BY s."CompanyName";
```

{/* The same highlight as the video: the Speedy Express row, in grey — the finding, no verdict. */}

<div className="[&_tbody_tr:nth-child(3)]:bg-[rgb(var(--hl-grey)/var(--hl-row))] [&_tbody_tr:nth-child(3)_td]:font-bold">

| Courier                | Orders | Shipped, no date | Share % |
| ---------------------- | ------ | ---------------- | ------- |

Both tests are needed: cancelled and open orders never have a ship date, so `"ShippedDate" IS NULL` on its own would count them too.

SQL tells us where to look; people confirm it.

## Four rules for CASE

1. **The first true `WHEN` wins.** Put the narrow tests first.
2. **Write the `ELSE`**, unless the NULLs are the point. A row that no `WHEN` matches gets NULL, and NULL fails every comparison, including "not equal".
3. **`SUM(CASE …)` gives one column per status**, all in the same `GROUP BY`.
4. **A share is `100.0 * SUM(CASE …) / count(*)`**, with the decimal point, multiplied before the division, and printed next to its count.

The last two give only the question, and the whole query has to be written from scratch: price bands as columns, and the return rate of each category.

**One idea here has no koan, on purpose.** The share that comes back as 0 is the most expensive mistake on this page, and DuckDB, which the koans run on, keeps the fraction that PostgreSQL throws away. A koan would go green for the very query CloudBeaver shows as a column of zeros, so that rule lives here, in the video and in the flashcards instead. The share koans still ask for `100.0 *`: write it that way and your answer is right on both.
