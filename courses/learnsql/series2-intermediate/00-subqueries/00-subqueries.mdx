That question contains a second question: what is the average customer? Without SQL beyond Series 1, the only way to answer it is to run one query, write the number down, and paste it into a second query. This lesson shows how to let the database answer the first question inside the second one, with a **subquery**: a query in brackets that runs first, and whose result the outer query uses.

## Why the average cannot go in the WHERE

The obvious fix is to let the database calculate the average in the same place:

{/* The same highlight as the video: the refused line in red. */}

```sql file=./scripts/aggregate-in-where.sql {3}#err
SELECT "ProductName", "UnitPrice"
FROM "Products"
WHERE "UnitPrice" > AVG("UnitPrice");
```

PostgreSQL refuses it:

```
SQL Error [42803]: ERROR: aggregate functions are not allowed in WHERE
  Position: 71
```

This is the rule from the <a href="/academy/learn-sql/having-vs-where" target="_blank" rel="noopener" className="font-medium underline underline-offset-4">HAVING vs WHERE lesson</a>. `WHERE` looks at one row at a time, before anything has been added up, so when it runs there is no average to compare with. The average exists, but only as the result of a different query.

## A query in brackets

So give the `WHERE` that different query. Put it in brackets, where the pasted number was:

{/* The same highlight as the video: the two bracket lines in green. */}

```sql file=./scripts/above-average-price.sql {3-4}#good
SELECT "ProductName", "UnitPrice"
FROM "Products"
WHERE "UnitPrice" > (SELECT AVG("UnitPrice")
                     FROM "Products")
ORDER BY "UnitPrice" DESC;
```

The database runs the query in brackets first. It returns **one value**, the average price, and the outer query compares every product with that value, exactly as it did with the pasted-in 24.01. The result is the same 30 products. The difference is that tomorrow the brackets return tomorrow's average, and there is no number to keep up to date.

### Run the inside on its own

A subquery is a complete query. In CloudBeaver, select just the text inside the brackets and run it (CloudBeaver runs only the selected text). It should return what you expect, here a single number. If the inside returns something unexpected, the whole query cannot be right either.

1. Select only the part in brackets.
2. Run it on its own, and check that it returns what you expected.
3. Then run the whole query.

## One value, or the query stops

Now a question of our own: which products cost more than our drinks? Beverages are category 1, so the brackets return the beverages' prices:

{/* The same highlight as the video: the subquery's three lines in red. */}

```sql file=./scripts/dearer-than-beverages-error.sql {3-5}#err
SELECT "ProductName", "UnitPrice"
FROM "Products"
WHERE "UnitPrice" > (SELECT "UnitPrice"
                     FROM "Products"
                     WHERE "CategoryID" = 1);
```

```
SQL Error [21000]: ERROR: more than one row returned by a subquery used as an expression
```

There are ten beverages, so the brackets return ten prices, and `>` compares one value with one value. The error is really a question: which of the ten prices is meant? "More than every beverage" means more than the most expensive beverage, so ask for that one value with `MAX`:

{/* The same highlight as the video: the MAX line in green. */}

```sql file=./scripts/dearer-than-every-beverage.sql {3}#good
SELECT "ProductName", "UnitPrice"
FROM "Products"
WHERE "UnitPrice" > (SELECT MAX("UnitPrice")
                     FROM "Products"
                     WHERE "CategoryID" = 1)
ORDER BY "UnitPrice" DESC;
```

| ProductName         | UnitPrice |
| ------------------- | --------- |
| Harvest Chicken Pie | 81        |
| Spiced Meatballs    | 61.12     |
| Island Sausages     | 58.42     |
| Smoked Feta         | 53.04     |
| …                   | …         |
| Spiced Ham          | 39.32     |
| Old Town Relish     | 39.19     |

Fourteen products cost more than the most expensive beverage, Alpine Ale, at 39.1.

Two of the rows behind the "…" cost exactly the same, 43.12. `ORDER BY "UnitPrice"` does not say which of two equal prices comes first, so the database may return them in either order. When the order of tied rows matters, add a second column to the `ORDER BY`, such as `"ProductName"`.

## Three shapes

What a subquery returns decides where it can go:

| The brackets return | Shape | Where it goes |
| ------------------- | ----- | ------------- |
| one row, one column | a **value** | anywhere a single value can go: `WHERE x > (…)` |
| one column, many rows | a **list** | inside `IN (…)` |
| rows and columns | a **table** | in the `FROM`, like any table |

The queries above used a value. Next, a list.

## A list: IN

Royal Raisins, product 39, has been discontinued, and sales wants to tell the customers who bought it this year. **Which customers bought Royal Raisins in 2024?** The brackets return the customer of every 2024 order line for Royal Raisins, and `IN` keeps each customer whose `"CustomerID"` appears in that list:

{/* The same highlight as the video: the IN line, in grey. */}

```sql file=./scripts/royal-raisins-customers.sql {3}
SELECT "CompanyName"
FROM "Customers"
WHERE "CustomerID" IN (
  SELECT o."CustomerID"
  FROM "Orders" o
  JOIN "Order Details" d
    ON d."OrderID" = o."OrderID"
  WHERE d."ProductID" = 39
    AND o."OrderDate" >= DATE '2024-01-01'
)
ORDER BY "CompanyName";
```

Royal Raisins sold on 9 order lines in 2024, so it is tempting to predict 9 customers. The result has 8:

## Now the customers

Back to the manager's question: which customers spend more than the average customer? Same method as with prices. First, the average:

```sql file=./scripts/average-sale.sql
SELECT ROUND(AVG("UnitPrice" * "Quantity"
         * (1 - "Discount")), 2) AS "Average"
FROM "Order Details";
```

| Average |
| ------- |
| 595.13  |

Then the report from the last lesson, with a `HAVING` at the end that keeps the customers whose total is above 595.13:

{/* The same highlight as the video: the HAVING lines, in grey. */}

```sql file=./scripts/customers-above-the-average-line.sql {10-11}
SELECT c."CompanyName",
       ROUND(SUM(d."UnitPrice" * d."Quantity"
         * (1 - d."Discount")), 2) AS "Total sales"
FROM "Customers" c
JOIN "Orders" o
  ON o."CustomerID" = c."CustomerID"
JOIN "Order Details" d
  ON d."OrderID" = o."OrderID"
GROUP BY c."CompanyName"
HAVING SUM(d."UnitPrice" * d."Quantity"
         * (1 - d."Discount")) > 595.13
ORDER BY "Total sales" DESC;
```

## The average of what?

595.13 is the average of the money column in `"Order Details"`, and every row of that table is one order line. So 595.13 is the **average order line**. A customer's total is many order lines added together, so it almost always beats one line. The query compared each customer with an order line.

The one customer the query left out proves it. Upland Food Hall has placed a single order of two lines, worth 465.75 in total: less than one average line, and the only customer whose whole history is that small.

This is the question from the report lesson again: **one row represents what?** To compare a customer with the average customer, first build one total per customer, then take the average of those totals. That needs the third shape: a table in brackets.

## A table in brackets

{/* The same highlight as the video: the lines that open and close the table in brackets, in grey. */}

```sql file=./scripts/average-customer.sql {2,9}
SELECT ROUND(AVG("Total"), 2) AS "Average customer"
FROM (SELECT o."CustomerID",
             SUM(d."UnitPrice" * d."Quantity"
               * (1 - d."Discount"))
               AS "Total"
      FROM "Orders" o
      JOIN "Order Details" d
        ON d."OrderID" = o."OrderID"
      GROUP BY o."CustomerID") AS t;
```

| Average customer |
| ---------------- |
| 126193.54        |

The query in brackets returns a table with one row per customer and that customer's total. The outer query reads that table in its `FROM` and averages the totals.

The table in brackets is given a name, `AS t`. PostgreSQL 16 and DuckDB accept a subquery in `FROM` without a name, but older versions of PostgreSQL, MySQL and SQL Server refuse it, so always name it.

The two averages are far apart:

| Average of | Value |
| ---------- | ----- |
| an order line | 595.13 |
| a customer | 126193.54 |

Neither is wrong. They answer different questions, and the manager asked about customers.

### Customers above the average customer

Now put the table in brackets inside the `HAVING`. The brackets build the table of customer totals and return its average, a single value, and `HAVING` compares each customer's total with it:

{/* The same highlight as the video: the whole subquery, in grey. */}

```sql file=./scripts/customers-above-the-average-customer.sql {12-20}
SELECT c."CompanyName",
       ROUND(SUM(d."UnitPrice" * d."Quantity"
         * (1 - d."Discount")), 2) AS "Total sales"
FROM "Customers" c
JOIN "Orders" o
  ON o."CustomerID" = c."CustomerID"
JOIN "Order Details" d
  ON d."OrderID" = o."OrderID"
GROUP BY c."CompanyName"
HAVING SUM(d."UnitPrice" * d."Quantity"
         * (1 - d."Discount"))
     > (SELECT AVG(t."Total")
        FROM (SELECT o2."CustomerID",
                     SUM(d2."UnitPrice"
                       * d2."Quantity"
                       * (1 - d2."Discount")) AS "Total"
              FROM "Orders" o2
              JOIN "Order Details" d2
                ON d2."OrderID" = o2."OrderID"
              GROUP BY o2."CustomerID") AS t)
ORDER BY "Total sales" DESC;
```

The inner query uses different aliases, `o2` and `d2`, so it is clear which tables belong to which query.

### Reading a nested query

The last query works, but it is hard to read: brackets inside brackets inside a `HAVING`. Read it from the inside out: the innermost query builds a table of customer totals, the query around it averages them, and the outer query compares each customer with that average. A later lesson in this series gives each step a name, so a query like this reads from top to bottom.

## Ordered, and invoiced

The manager's note had a second line: **"2024: orders up 10% on last year, but invoicing is down. Which is it?"**

That is two totals for 2024. The first is the money the report already adds up, for the orders placed in 2024. The second comes from `"Invoices"`, a table with one row for every invoice the company sent: the order it bills, the date it was sent, and the amount.

### Two values, side by side

Each total is a value in brackets, and a value can go anywhere a single value can go, including the select list. So one query can return both, next to each other:

{/* The same highlight as the video: the two lines that open the brackets' FROM, in grey. */}

```sql file=./scripts/ordered-and-invoiced-2024.sql {3,9}
SELECT (SELECT ROUND(SUM(d."UnitPrice" * d."Quantity"
                 * (1 - d."Discount")), 2)
        FROM "Order Details" d
        JOIN "Orders" o
          ON o."OrderID" = d."OrderID"
        WHERE o."OrderDate" >= DATE '2024-01-01'
          AND o."OrderDate" <  DATE '2025-01-01') AS "Ordered 2024",
       (SELECT ROUND(SUM("Amount"), 2)
        FROM "Invoices"
        WHERE "InvoiceDate" >= DATE '2024-01-01'
          AND "InvoiceDate" <  DATE '2025-01-01') AS "Invoiced 2024";
```

| Ordered 2024 | Invoiced 2024 |
| ------------ | ------------- |
| 3628572.55   | 3190372.69    |

The first bracket is the report's money, joined to `"Orders"` so that it can see `"OrderDate"`, and kept for the orders placed in 2024. The second adds up the invoices sent in 2024. Select either bracket on its own and run it: each returns one number.

The outer `SELECT` has no `FROM`, because all it does is return the two values. PostgreSQL and DuckDB accept that; older versions of Oracle need `FROM dual` at the end.

### Neither total is wrong

It is tempting to ask which of the two numbers is wrong. Neither is. **The two totals answer different questions.** What customers ordered measures demand: how much they asked us for. What was invoiced is what the company actually billed. The report answered the first question; the manager's note is about the gap between the two. In 2024, orders grew, and invoicing fell.

Why would invoicing fall while orders grew? That is the question the next lessons follow, one step at a time: **what is missing, where, since when, and how much?**

## Before you trust a subquery

1. **Run the inside on its own.**
2. **Check its shape:** a value, a list or a table. The shape decides where it can go, and the wrong shape stops the query with an error.
3. **Check its grain:** one row of the inside represents what? The wrong grain does not produce an error. It produces 118 customers who are nearly all "above average".
