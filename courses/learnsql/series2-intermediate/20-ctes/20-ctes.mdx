## Right, and hard to read

The last two lessons ended on queries that return the right answer and are hard to read: brackets inside brackets, a subquery in `FROM` next to a `LEFT JOIN`. This lesson adds one tool that changes how such queries read, without changing what they return: `WITH`, which gives each step of a query a **name**.

Every query below runs on the Northwind database on PostgreSQL. Write each one in CloudBeaver and compare the result with the table under it. If that is not set up yet, the [Learn Data](/docs/learn-data) guide gets it running.

## The nested version

Here is the query from the <a href="/academy/learn-sql/subqueries" target="_blank" rel="noopener" className="font-medium underline underline-offset-4">subqueries lesson</a> that finds the customers who spend more than the average customer:

{/* The same highlight as the video: the innermost brackets, in grey. */}

```sql file=./scripts/customers-above-the-average-customer-nested.sql {13-20}
SELECT c."CompanyName",
       ROUND(SUM(d."UnitPrice" * d."Quantity"
         * (1 - d."Discount")), 2) AS "Total sales"
FROM "Customers" c
JOIN "Orders" o
  ON o."CustomerID" = c."CustomerID"
JOIN "Order Details" d
  ON d."OrderID" = o."OrderID"
GROUP BY c."CompanyName"
HAVING SUM(d."UnitPrice" * d."Quantity"
         * (1 - d."Discount"))
     > (SELECT AVG(t."Total")
        FROM (SELECT o2."CustomerID",
                     SUM(d2."UnitPrice"
                       * d2."Quantity"
                       * (1 - d2."Discount")) AS "Total"
              FROM "Orders" o2
              JOIN "Order Details" d2
                ON d2."OrderID" = o2."OrderID"
              GROUP BY o2."CustomerID") AS t)
ORDER BY "Total sales" DESC;
```

It has to be read from the inside out. The innermost brackets build one total per customer. The brackets around them average those totals. The outer query compares each customer with that average.

## WITH: give the brackets a name

Take the innermost brackets out, give them a name, and write them first, after the word `WITH`. The query below them reads the name as if it were a table:

{/* The same highlight as the video: WITH and the FROM that uses the name, in green. */}

```sql file=./scripts/average-customer-with.sql {1,11}#good
WITH customer_totals AS (
  SELECT o."CustomerID",
         SUM(d."UnitPrice" * d."Quantity"
           * (1 - d."Discount")) AS "Total"
  FROM "Orders" o
  JOIN "Order Details" d
    ON d."OrderID" = o."OrderID"
  GROUP BY o."CustomerID"
)
SELECT ROUND(AVG("Total"), 2) AS "Average customer"
FROM customer_totals;
```

| Average customer |
| ---------------- |
| 2326.13          |

The same average as in the subqueries lesson. The part in brackets after `WITH customer_totals AS` is a **CTE**, a common table expression: a subquery with a name, written before the query that uses it.

A CTE is not stored anywhere. The name exists only inside this one statement, up to its semicolon. Inside the statement, though, it can be used as often as you need.

## Use a step twice

The nested version built the customer totals twice: once for the list of customers and once inside the average. With a name, the same step feeds both:

{/* The same highlight as the video: the two uses of customer_totals, in green. */}

```sql file=./scripts/customers-above-the-average-customer-with.sql {12,15-16}#good
WITH customer_totals AS (
  SELECT o."CustomerID",
         SUM(d."UnitPrice" * d."Quantity"
           * (1 - d."Discount")) AS "Total"
  FROM "Orders" o
  JOIN "Order Details" d
    ON d."OrderID" = o."OrderID"
  GROUP BY o."CustomerID"
)
SELECT c."CompanyName",
       ROUND(t."Total", 2) AS "Total sales"
FROM customer_totals t
JOIN "Customers" c
  ON c."CustomerID" = t."CustomerID"
WHERE t."Total" > (SELECT AVG("Total")
                   FROM customer_totals)
ORDER BY "Total sales" DESC;
```

| CompanyName                | Total sales |
| -------------------------- | ----------- |
| Cactus Comidas para llevar | 4567.8      |
| Blauer See Delikatessen    | 4318.8      |
| Frankenversand             | 4267.27     |
| …                          | …           |
| Morgenstern Gesundkost     | 3289.13     |
| Around the Horn            | 2701.58     |
| Great Lakes Food Market    | 2683.28     |

The same nine customers as the nested query, and now it reads from top to bottom: first the customer totals, then the customers whose total is above their average.

## Steps that read steps

One `WITH` can define several steps, separated by commas, and **each step can read the steps above it**. Here is the June product report from the <a href="/academy/learn-sql/multi-table-joins-duplicate-rows" target="_blank" rel="noopener" className="font-medium underline underline-offset-4">multi-table joins lesson</a> as three steps: June's order lines, the units per product, and the report:

{/* The same highlight as the video: the two step names in green, and june_units reading june_lines. */}

```sql file=./scripts/june-report-with.sql {1,9,12}
WITH june_lines AS (
  SELECT d."ProductID", d."Quantity"
  FROM "Order Details" d
  JOIN "Orders" o
    ON o."OrderID" = d."OrderID"
  WHERE o."OrderDate" >= DATE '2024-06-01'
    AND o."OrderDate" <  DATE '2024-07-01'
),
june_units AS (
  SELECT "ProductID",
         sum("Quantity") AS "June units"
  FROM june_lines
  GROUP BY "ProductID"
)
SELECT p."ProductName", u."June units"
FROM "Products" p
LEFT JOIN june_units u
  ON u."ProductID" = p."ProductID"
ORDER BY p."ProductName";
```

`june_units` reads from `june_lines`, and the final query joins every product to `june_units`.

### Check that the answer did not move

A rewrite is only correct if it returns exactly what the original returned. The quickest check is to count the rows and add up the totals, on the original and on the rewrite, and compare. Add the report as one more step and count it:

```sql file=./scripts/june-report-with-check.sql
WITH june_lines AS (
  SELECT d."ProductID", d."Quantity"
  FROM "Order Details" d
  JOIN "Orders" o
    ON o."OrderID" = d."OrderID"
  WHERE o."OrderDate" >= DATE '2024-06-01'
    AND o."OrderDate" <  DATE '2024-07-01'
),
june_units AS (
  SELECT "ProductID",
         sum("Quantity") AS "June units"
  FROM june_lines
  GROUP BY "ProductID"
),
report AS (
  SELECT p."ProductName", u."June units"
  FROM "Products" p
  LEFT JOIN june_units u
    ON u."ProductID" = p."ProductID"
)
SELECT count(*) AS "Rows",
       count("June units") AS "Sold",
       sum("June units") AS "Units"
FROM report;
```

## The tidy-up that changed the answer

The query still feels long. A tempting tidy-up: one step with every order line and its date, and the June test moved to the final `WHERE`, where filters usually go:

{/* The same highlight as the video: the moved WHERE, in red. */}

```sql file=./scripts/june-report-tidied.sql {13-14}#err
WITH order_lines AS (
  SELECT d."ProductID", d."Quantity",
         o."OrderDate"
  FROM "Order Details" d
  JOIN "Orders" o
    ON o."OrderID" = d."OrderID"
)
SELECT p."ProductName",
       sum(l."Quantity") AS "June units"
FROM "Products" p
LEFT JOIN order_lines l
  ON l."ProductID" = p."ProductID"
WHERE l."OrderDate" >= DATE '2024-06-01'
  AND l."OrderDate" <  DATE '2024-07-01'
GROUP BY p."ProductName"
ORDER BY p."ProductName";
```

| ProductName                 | June units |
| --------------------------- | ---------- |
| Aniseed Syrup               | 3          |
| Boston Crab Meat            | 8          |
| Chai                        | 12         |
| Chang                       | 10         |
| Chef Antons Cajun Seasoning | 2          |
| Scottish Longbreads         | 5          |

Six rows. The units still add up to 40, so a check on the total alone would pass. The row count does not:

```sql file=./scripts/june-report-tidied-check.sql
WITH order_lines AS (
  SELECT d."ProductID", d."Quantity",
         o."OrderDate"
  FROM "Order Details" d
  JOIN "Orders" o
    ON o."OrderID" = d."OrderID"
),
report AS (
  SELECT p."ProductName",
         sum(l."Quantity") AS "June units"
  FROM "Products" p
  LEFT JOIN order_lines l
    ON l."ProductID" = p."ProductID"
  WHERE l."OrderDate" >= DATE '2024-06-01'
    AND l."OrderDate" <  DATE '2024-07-01'
  GROUP BY p."ProductName"
)
SELECT count(*) AS "Rows",
       count("June units") AS "Sold",
       sum("June units") AS "Units"
FROM report;
```

| Rows | Sold | Units |
| ---- | ---- | ----- |
| 6    | 6    | 40    |

The `WHERE` now tests `l."OrderDate"`, a column that comes from the `LEFT JOIN`. For a product with no June line that column is NULL, the test is not true, and the row is removed — the same problem as in the JOINs lessons. The tidy-up changed the answer from 20 products to 6.

The same check on both versions:

| Version                 | Rows | Sold | Units |
| ----------------------- | ---- | ---- | ----- |
| june_lines → june_units | 20   | 6    | 40    |
| the tidy-up             | 6    | 6    | 40    |

**Keep a filter inside the step it narrows.** In the first version the June test runs inside `june_lines`, before any join, where it cannot remove a product.

## Look inside one step

When a query with steps returns something unexpected, look at one step on its own: keep the `WITH` and point the final `SELECT` at the step you want to see.

{/* The same highlight as the video: the SELECT that reads one step, in green. */}

```sql file=./scripts/june-lines-step.sql {10-11}#good
WITH june_lines AS (
  SELECT d."OrderID", d."ProductID",
         d."Quantity"
  FROM "Order Details" d
  JOIN "Orders" o
    ON o."OrderID" = d."OrderID"
  WHERE o."OrderDate" >= DATE '2024-06-01'
    AND o."OrderDate" <  DATE '2024-07-01'
)
SELECT *
FROM june_lines
ORDER BY "OrderID", "ProductID";
```

| OrderID | ProductID | Quantity |
| ------- | --------- | -------- |
| 4       | 1         | 12       |
| 4       | 2         | 10       |
| 5       | 3         | 3        |
| 6       | 4         | 2        |
| 6       | 5         | 5        |
| 7       | 6         | 8        |

Six June lines from four orders, adding up to 40 units. This step is correct, so the problem, if there is one, is in a later step.

## The case file: the report, as named steps

The case this series follows: in Northwind, a third of what was sold, 19169 of 58153.31, is on orders that have no ship date. The <a href="/academy/learn-sql/multi-table-joins-duplicate-rows" target="_blank" rel="noopener" className="font-medium underline underline-offset-4">multi-table joins lesson</a> found where that money sits, by sales rep and by courier: the value of each order added up first, in brackets, and joined to the orders with no ship date. That is a report somebody re-runs every week, so it has to be easy to read.

As named steps: `open_orders` keeps the orders with no `"ShippedDate"`, `order_value` adds up the order lines of each one, reading the step above it, and the final query joins both to the rep and the courier:

{/* The same highlight as the video: the two step names in green; order_value reading open_orders,
    and the final query reading both steps, in grey. */}

```sql file=./scripts/open-orders-by-rep-and-courier-with.sql {1,6,10,19-20}
WITH open_orders AS (
  SELECT "OrderID", "EmployeeID", "ShipVia", "Freight"
  FROM "Orders"
  WHERE "ShippedDate" IS NULL
),
order_value AS (
  SELECT o."OrderID",
         SUM(d."UnitPrice" * d."Quantity"
           * (1 - d."Discount")) AS "Order value"
  FROM open_orders o
  JOIN "Order Details" d ON d."OrderID" = o."OrderID"
  GROUP BY o."OrderID"
)
SELECT e."FirstName" AS "Rep",
       s."CompanyName" AS "Courier",
       count(*) AS "Orders",
       ROUND(SUM(v."Order value"), 2) AS "Sales",
       SUM(o."Freight") AS "Freight"
FROM open_orders o
JOIN order_value v ON v."OrderID" = o."OrderID"
JOIN "Employees" e ON e."EmployeeID" = o."EmployeeID"
JOIN "Shippers" s ON s."ShipperID" = o."ShipVia"
GROUP BY e."FirstName", s."CompanyName"
ORDER BY "Sales" DESC;
```

## For reading, not for speed

Do not expect a CTE to make a query faster. The database is free to treat a CTE the same way as the subquery it replaced. A CTE is for the person reading the query, and query speed is covered in Series 3.

## Four rules for WITH

1. **Name a step, then use the name.**
2. **A step can read the steps above it**, and a step can be used more than once.
3. **After any rewrite, compare the rows and the totals with the original.**
4. **Keep a filter inside the step it narrows.**
