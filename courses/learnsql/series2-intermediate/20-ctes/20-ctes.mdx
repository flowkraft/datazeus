## Right, and hard to read

The last two lessons ended on queries that return the right answer and are hard to read: brackets inside brackets, a subquery in `FROM` next to a `LEFT JOIN`, and in the freight report the same month written twice. This lesson adds one tool that changes how such queries read, without changing what they return: `WITH`, which gives each step of a query a **name**.

Every query below runs on Northwind Company, the dataset installed in the <a href="/academy/learn-sql/subqueries" target="_blank" rel="noopener" className="font-medium underline underline-offset-4">first lesson of this series</a>, and assumes `SET search_path TO northwind_co_s;` has been run in the CloudBeaver editor. Write each query and compare the result with the table under it.

## The nested version

Here is the query from the <a href="/academy/learn-sql/subqueries" target="_blank" rel="noopener" className="font-medium underline underline-offset-4">subqueries lesson</a> that finds the customers who spend more than the average customer:

{/* The same highlight as the video: the innermost brackets, in grey. */}

```sql file=./scripts/customers-above-the-average-customer-nested.sql {13-20}
SELECT c."CompanyName",
       ROUND(SUM(d."UnitPrice" * d."Quantity"
         * (1 - d."Discount")), 2) AS "Total sales"
FROM "Customers" c
JOIN "Orders" o
  ON o."CustomerID" = c."CustomerID"
JOIN "Order Details" d
  ON d."OrderID" = o."OrderID"
GROUP BY c."CompanyName"
HAVING SUM(d."UnitPrice" * d."Quantity"
         * (1 - d."Discount"))
     > (SELECT AVG(t."Total")
        FROM (SELECT o2."CustomerID",
                     SUM(d2."UnitPrice"
                       * d2."Quantity"
                       * (1 - d2."Discount")) AS "Total"
              FROM "Orders" o2
              JOIN "Order Details" d2
                ON d2."OrderID" = o2."OrderID"
              GROUP BY o2."CustomerID") AS t)
ORDER BY "Total sales" DESC;
```

It has to be read from the inside out. The innermost brackets build one total per customer. The brackets around them average those totals. The outer query compares each customer with that average.

## WITH: give the brackets a name

Take the innermost brackets out, give them a name, and write them first, after the word `WITH`. The query below them reads the name as if it were a table:

{/* The same highlight as the video: WITH and the FROM that uses the name, in green. */}

```sql file=./scripts/average-customer-with.sql {1,11}#good
WITH customer_totals AS (
  SELECT o."CustomerID",
         SUM(d."UnitPrice" * d."Quantity"
           * (1 - d."Discount")) AS "Total"
  FROM "Orders" o
  JOIN "Order Details" d
    ON d."OrderID" = o."OrderID"
  GROUP BY o."CustomerID"
)
SELECT ROUND(AVG("Total"), 2) AS "Average customer"
FROM customer_totals;
```

| Average customer |
| ---------------- |
| 126193.54        |

The same average as in the subqueries lesson. The part in brackets after `WITH customer_totals AS` is a **CTE**, a common table expression: a subquery with a name, written before the query that uses it.

A CTE is not stored anywhere. The name exists only inside this one statement, up to its semicolon. Inside the statement, though, it can be used as often as you need.

## Use a step twice

The nested version built the customer totals twice: once for the list of customers and once inside the average. With a name, the same step feeds both:

{/* The same highlight as the video: the two uses of customer_totals, in green. */}

```sql file=./scripts/customers-above-the-average-customer-with.sql {12,15-16}#good
WITH customer_totals AS (
  SELECT o."CustomerID",
         SUM(d."UnitPrice" * d."Quantity"
           * (1 - d."Discount")) AS "Total"
  FROM "Orders" o
  JOIN "Order Details" d
    ON d."OrderID" = o."OrderID"
  GROUP BY o."CustomerID"
)
SELECT c."CompanyName",
       ROUND(t."Total", 2) AS "Total sales"
FROM customer_totals t
JOIN "Customers" c
  ON c."CustomerID" = t."CustomerID"
WHERE t."Total" > (SELECT AVG("Total")
                   FROM customer_totals)
ORDER BY "Total sales" DESC;
```

| CompanyName      | Total sales |
| ---------------- | ----------- |
| Fjord Foods      | 797164      |
| Yarrow Pantry    | 786022.56   |
| Quayside Traders | 783579.03   |
| …                | …           |
| Amber Grocers    | 186853.36   |
| Emerald Grocers  | 175249.7    |

The same 30 customers as the nested query, and now it reads from top to bottom: first the customer totals, then the customers whose total is above their average.

## Steps that read steps

One `WITH` can define several steps, separated by commas, and **each step can read the steps above it**. Here is the Dairy report from the <a href="/academy/learn-sql/multi-table-joins-duplicate-rows" target="_blank" rel="noopener" className="font-medium underline underline-offset-4">multi-table joins lesson</a> (every Dairy product and its units in May 2024) as steps: May's order lines, the units per product, and the report:

{/* The same highlight as the video: the two step names in green, and may_units reading may_lines. */}

```sql file=./scripts/dairy-report-with.sql {1,9,12}
WITH may_lines AS (
  SELECT d."ProductID", d."Quantity"
  FROM "Order Details" d
  JOIN "Orders" o
    ON o."OrderID" = d."OrderID"
  WHERE o."OrderDate" >= DATE '2024-05-01'
    AND o."OrderDate" <  DATE '2024-06-01'
),
may_units AS (
  SELECT "ProductID",
         sum("Quantity") AS "May units"
  FROM may_lines
  GROUP BY "ProductID"
)
SELECT p."ProductName", u."May units"
FROM "Products" p
LEFT JOIN may_units u
  ON u."ProductID" = p."ProductID"
WHERE p."CategoryID" = 4
ORDER BY p."ProductName";
```

`may_units` reads from `may_lines`, and the final query joins every Dairy product to `may_units`.

### Check that the answer did not move

A rewrite is only correct if it returns exactly what the original returned. The quickest check is to count the rows and add up the totals, on the original and on the rewrite, and compare. Add the report as one more step and count it:

```sql file=./scripts/dairy-report-with-check.sql
WITH may_lines AS (
  SELECT d."ProductID", d."Quantity"
  FROM "Order Details" d
  JOIN "Orders" o
    ON o."OrderID" = d."OrderID"
  WHERE o."OrderDate" >= DATE '2024-05-01'
    AND o."OrderDate" <  DATE '2024-06-01'
),
may_units AS (
  SELECT "ProductID",
         sum("Quantity") AS "May units"
  FROM may_lines
  GROUP BY "ProductID"
),
report AS (
  SELECT p."ProductName", u."May units"
  FROM "Products" p
  LEFT JOIN may_units u
    ON u."ProductID" = p."ProductID"
  WHERE p."CategoryID" = 4
)
SELECT count(*) AS "Rows",
       count("May units") AS "Sold",
       sum("May units") AS "Units"
FROM report;
```

## One filter, and every use of the step sees it

The sales-and-freight report from the last lesson is correct, and it writes May's range twice: once in the brackets that add up the sales, once in the brackets that add up the freight.

{/* The same highlight as the video: the two copies of May's range, in grey. */}

```sql file=../15-multi-table-joins-duplicate-rows/scripts/sales-and-freight-aggregated-first.sql {9-10,16-17}
SELECT c."CompanyName", s."Total sales", f."Freight"
FROM "Customers" c
JOIN (SELECT o."CustomerID",
             ROUND(SUM(d."UnitPrice" * d."Quantity"
               * (1 - d."Discount")), 2) AS "Total sales"
      FROM "Orders" o
      JOIN "Order Details" d
        ON d."OrderID" = o."OrderID"
      WHERE o."OrderDate" >= DATE '2024-05-01'
        AND o."OrderDate" <  DATE '2024-06-01'
      GROUP BY o."CustomerID") AS s
  ON s."CustomerID" = c."CustomerID"
JOIN (SELECT "CustomerID",
             SUM("Freight") AS "Freight"
      FROM "Orders"
      WHERE "OrderDate" >= DATE '2024-05-01'
        AND "OrderDate" <  DATE '2024-06-01'
      GROUP BY "CustomerID") AS f
  ON f."CustomerID" = c."CustomerID"
ORDER BY f."Freight" DESC
LIMIT 5;
```

Nothing is wrong with it today. The cost comes with the next edit. Move the sales brackets to June, forget the freight brackets, and the query still runs without an error: it reports 39 customers, with June's sales next to May's freight.

As steps, the month's orders are one step, `month_orders`, and both the sales step and the freight step read it:

{/* The same highlight as the video: the May range in green, and the two steps that read month_orders in grey. */}

```sql file=./scripts/sales-and-freight-with.sql {4-5,11,18}#good
WITH month_orders AS (
  SELECT "OrderID", "CustomerID", "Freight"
  FROM "Orders"
  WHERE "OrderDate" >= DATE '2024-05-01'
    AND "OrderDate" <  DATE '2024-06-01'
),
sales AS (
  SELECT o."CustomerID",
         ROUND(SUM(d."UnitPrice" * d."Quantity"
           * (1 - d."Discount")), 2) AS "Total sales"
  FROM month_orders o
  JOIN "Order Details" d ON d."OrderID" = o."OrderID"
  GROUP BY o."CustomerID"
),
freight AS (
  SELECT "CustomerID",
         SUM("Freight") AS "Freight"
  FROM month_orders
  GROUP BY "CustomerID"
)
SELECT c."CompanyName", s."Total sales", f."Freight"
FROM "Customers" c
JOIN sales s ON s."CustomerID" = c."CustomerID"
JOIN freight f ON f."CustomerID" = c."CustomerID"
ORDER BY f."Freight" DESC
LIMIT 5;
```

## The merge that multiplied the freight

`sales` and `freight` both group by the customer, and both return one row per customer. Two steps that do the same grouping look like one step written twice, and the obvious tidy-up is to write them as one — one step, one join, both numbers:

{/* The amber is for a query that RUNS: the merged freight and the join that feeds it. */}

```sql file=./scripts/sales-and-freight-merged.sql {11,13}#warn
WITH month_orders AS (
  SELECT "OrderID", "CustomerID", "Freight"
  FROM "Orders"
  WHERE "OrderDate" >= DATE '2024-05-01'
    AND "OrderDate" <  DATE '2024-06-01'
),
totals AS (
  SELECT o."CustomerID",
         ROUND(SUM(d."UnitPrice" * d."Quantity"
           * (1 - d."Discount")), 2) AS "Total sales",
         SUM(o."Freight") AS "Freight"
  FROM month_orders o
  JOIN "Order Details" d ON d."OrderID" = o."OrderID"
  GROUP BY o."CustomerID"
)
SELECT c."CompanyName", t."Total sales", t."Freight"
FROM "Customers" c
JOIN totals t ON t."CustomerID" = c."CustomerID"
ORDER BY t."Freight" DESC
LIMIT 5;
```

It runs, and every sales figure in it is right to the cent. The freight is not, and the report now opens on a different company: Quayside Wholefoods was fifth on freight a moment ago, on 571.5.

`month_orders` holds **one row per order**. Joining it to `"Order Details"` gives **one row per order line**, so `SUM(o."Freight")` adds each order's freight once for every line that order has. Quayside's two May orders carry seven lines between them — 3.86 on one line and 567.64 on six — so the step returns 3.86 + 6 × 567.64 = 3409.7 where the truth is 571.5. This is the fan-out from the joins lesson, arriving through a step that has a name on it.

The sales column is untouched, because a sale **is** a line: `sales` was always meant to be added up over the joined lines, and the join is where it belongs. Only the freight was at the wrong grain.

**One step, one grain.** A step is not safe because it has a name. Name it after the grain it holds — `month_orders` is one row per order, `sales` is one row per customer over the order lines — and you can say out loud what a `SUM` over it is adding up.

## Look inside one step

When a query with steps returns something that looks wrong, look at one step on its own: keep the `WITH` and point the final `SELECT` at the step you want to see. Narrow it to the rows in doubt. The merged report put Quayside Wholefoods at the top of May on 3409.7, so read what the step it was built from actually holds:

{/* The same highlight as the video: the SELECT that reads one step, in green. */}

```sql file=./scripts/month-orders-step.sql {7-8}#good
WITH month_orders AS (
  SELECT "OrderID", "CustomerID", "Freight"
  FROM "Orders"
  WHERE "OrderDate" >= DATE '2024-05-01'
    AND "OrderDate" <  DATE '2024-06-01'
)
SELECT *
FROM month_orders
WHERE "CustomerID" = 'QUAY3'
ORDER BY "OrderID";
```

| OrderID | CustomerID | Freight |
| ------- | ---------- | ------- |
| 8415    | QUAY3      | 3.86    |
| 8472    | QUAY3      | 567.64  |

Two May orders, and their freight adds up to 571.5 — the figure the two-step report shows. The step is correct, so the mistake was in the step that read it: 3.86 + 6 × 567.64 is where 3409.7 came from. Any step can be run on its own like this, which is half the reason to give them names.

## For reading, not for speed

Do not expect a CTE to make a query faster. The database is free to treat a CTE the same way as the subquery it replaced. A CTE is for the person reading the query, and query speed is covered in Series 3.

**A CTE is not a temporary table.** Naming a step does not store its answer anywhere. `customer_totals` is read twice at the top of this page, and the database is free to work it out twice. If what you need is the answer stored rather than the question named, a CTE is the wrong tool for it — that is what a table or a view is for.

## Four rules for WITH

1. **Name a step, then use the name.**
2. **A step can read the steps above it**, and a step can be used more than once.
3. **Write a filter once, inside the step it narrows.**
4. **One step, one grain** — and check the totals a join can multiply.
