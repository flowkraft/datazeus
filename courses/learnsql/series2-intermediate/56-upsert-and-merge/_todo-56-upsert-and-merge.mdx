    ── WHY THIS EPISODE, SPECIFICALLY ──────────────────────────────────────
    NEW 2026-09-19, split from Series 2 · 55, which carried too much. The curriculum.yaml comment above this
    episode has the full reasoning.
    GOAL: insert-or-update in one statement, and an insert you can run twice.
    SQL: INSERT … ON CONFLICT DO NOTHING; ON CONFLICT (key) DO UPDATE SET … = EXCLUDED.…; MERGE.
    THE FAILURE THAT EARNS IT: an import script run twice. Without ON CONFLICT the second run either
    duplicates every row or dies on the unique constraint, and the beginner's instinct is SELECT-then-INSERT,
    which is a race. DO NOTHING is the idempotent load; DO UPDATE is upsert in one statement.
    MERGE, ONE BEAT: the standard spelling (SQL:2003; PostgreSQL 15+, DuckDB 1.4+, and the only one on SQL
    Server and Oracle). Write the same upsert as MERGE. Its koan needs the koan runner's DuckDB upgraded from
    1.1.3 to 1.4.4.0 first (tests/pom.xml; curriculum.yaml, Series 2 header). The other engines' spellings (MySQL's ON DUPLICATE KEY UPDATE and the rest) are Series 4 · 05's.
    THE EXAMPLE: a supplier's price list — some products already exist (update the price), some are new
    (insert them). Practice on a copy made with Series 2 · 22's CREATE TABLE AS, with its key added: ON
    CONFLICT needs a key to conflict on, and a CREATE TABLE AS copy has none until you add it.
    DO NOT LET IT GROW INTO A PIPELINE LESSON: ETL & Data Pipelines, Series 1 · 25 owns re-runnable loads at
