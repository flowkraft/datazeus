    ── COVER ───────────────────────────────────────────────────────────────
      AN EXPORT IS A QUERY PLUS A CONTRACT. The query decides which rows; the contract
                            decides how a receiver reads them. The contract is every choice
                            below, and a receiver never sees any of them written down unless
                            you write them down.
      THE DAY               COPY (SELECT … WHERE "OrderDate" is 2024-12-23) TO a file, one
                            file per day, named after the day: 12 orders, 591.26 of freight.
                            Naming by the day is what makes the re-run in 1 · 30 overwrite the
                            same file instead of adding a second one.
      NULL                  2 of the 12 are unshipped. ShippedDate NULL is written as an
                            empty field, and read back as NULL. S has no empty strings, so
                            write one row yourself with '' next to a NULL: in a plain CSV they
                            are the same empty field, and the receiver cannot tell "none" from
                            "not recorded". That ambiguity is the CRM's problem in 1 · 20.
      QUOTING               9922's note is "If late, tell Tessa Young before noon." — one
                            comma, so the field is quoted, or the row has one column too many.
                            Then a WebOrders.Payload: JSON, every one full of quotes and
                            commas, and the writer doubles each inner quote. Show the bytes.
                            A hand-rolled writer that joins values with commas breaks here.
      TYPES DO NOT TRAVEL   Read the file back and the day is still 12 rows and 591.26, but
                            OrderID is BIGINT and Freight DOUBLE: a CSV carries text, and the
                            reader guessed. DECIMAL(19,4) went out as 43.8200 and came back as
                            a float. The receiver's types are the receiver's guess unless the
                            contract states them.
      LEADING ZEROS         04669 (order 9927, to Berlin) is a postal code, not a
                            number. DuckDB's reader keeps it as text; a spreadsheet opening
                            the same file does not. 1,041 of S's 10,000 orders ship to a code
                            that starts with 0.
      WHOSE DISK            DuckDB's COPY … TO writes on YOUR machine. PostgreSQL's COPY … TO
                            'file' writes on the DATABASE SERVER's disk, which from a client is
                            nowhere you can reach; from a client it is \copy in psql, or COPY
                            … TO STDOUT. The same statement, two different places.
      PARQUET, ONE PARAGRAPH  COPY … TO (FORMAT parquet) carries the types and NULL with it,
                            which removes three of the problems above. CSV stays the lowest
                            common denominator, which is why most hand-overs still use it.
                            Data Warehousing Series 2 owns the file format.
