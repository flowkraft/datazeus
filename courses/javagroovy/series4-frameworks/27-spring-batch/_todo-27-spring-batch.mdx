    THIS IS THE "WHAT IS A JOB" EPISODE, and it comes BEFORE 30, 35, 40 and 45 on purpose:
    those four are all about WHEN something runs and none of them says anything about what
    happens inside the run. Scheduling a method that loads 500,000 rows automates a job that
    cannot survive an interruption.

    WHAT IT BUYS, all of it left open by Series 1-3:
      CHUNKS    — Series 2 · 35 (batching, round trips) and 2 · 40 (streaming, rows held) as a
                  framework. The chunk size IS the batch size, so the counters from those two
                  episodes are the oracle here. No new machinery, no stopwatch.
      RESTART   — the JobRepository keeps execution state in a database, so a job that died at
                  chunk 400 resumes at chunk 400 rather than at zero.
      RETRY/SKIP— per item. One poisoned row need not kill a 500,000-row load.
      IDENTITY  — a job instance is (name + JobParameters), and Spring Batch REFUSES to run a
                  completed one again: JobInstanceAlreadyCompleteException. Idempotency
                  enforced by the framework instead of by your SQL.

## What goes wrong

{/* BEAT 4 — the failure this prevents, and how you would notice it in real data.
    Every episode in this track earns its place by preventing a wrong number or a
    job that dies at 3 a.m. Name that here.

    THE FAILURE IT PREVENTS: a load that died at row 400,000 of 500,000 and was simply run
    again from the top — so 400,000 rows are now in the table twice, and nothing threw.

    THE FAILURE IT CAUSES, and say this too: JobParameters identity means a job whose
    parameters never change will refuse to run a second time, which is astonishing the first
    time it happens in production. The usual fix is a run date or a run id parameter — and
    the moment you add one, you have opted out of the very protection you came for. Make the
    reader see both sides. */}
