     COVER: the write path, because it explains why this engine is fast and why deletes hurt.
     A write goes to the commit log and a memtable in memory, is acknowledged, and is later
     flushed to an immutable SSTable. NOTHING IS EVER MODIFIED IN PLACE. That is the LSM tree,
     and it is why writes are close to sequential and close to free.
     THE READ PATH AS THE CONSEQUENCE: a read may have to consult several SSTables plus the
     memtable and merge by timestamp. Bloom filters keep that cheap, most of the time.
     LAST WRITE WINS, by timestamp, with no conflict detection — so two concurrent updates to
     the same cell do not conflict, one simply disappears. Say it plainly.
