     ADDED 2026-09-07. An academy-wide audit of pre-aggregation found materialized views
     taught as a CONCEPT (Data Warehousing) and as ONE ENGINE'S behaviour (Oracle's MVs with
     query rewrite, its Series 3 · 15) — while this track, which has the same capability
     under a different name, never mentioned it. Zero hits for "indexed view" in this file
     before today, which is exactly the kind of silence a delta track exists to prevent.
     WHAT IT IS: a view with a UNIQUE CLUSTERED INDEX on it. The result stops being a query
     and becomes stored, maintained rows.
     THE DELTA FACT, and the reason for the episode: THE OPTIMIZER CAN SUBSTITUTE IT
     AUTOMATICALLY for queries written against the BASE TABLES, so code nobody edited gets
     faster. That is NOT true of a PostgreSQL materialized view, which only helps a query
     that names it. It IS true of Oracle's MVs and Db2's MQTs — one line so the reader
     recognises the family, and let Database X vs Database Y own the comparison.
     AND THE EDITION CATCH, in the same breath because it decides whether any of the above
     happens: automatic matching is an ENTERPRISE and Developer behaviour. On Standard the
     view is still maintained and still correct, but the query must name it and use
     WITH (NOEXPAND). A team on Standard that reads about indexed views, measures nothing
     and concludes the feature does not work has met exactly this.
     THE REQUIREMENTS ARE STRICT, and listing them is most of the practical value:
       WITH SCHEMABINDING, two-part names, deterministic expressions only
       COUNT_BIG(*) rather than COUNT(*) — a real and frequent first failure
       no outer joins, no subqueries, no derived tables
       the SET options in force BOTH at creation AND at query time — which is Series 1 · 15
         arriving again, and the callback should be explicit: an app connection whose
         ANSI_NULLS or QUOTED_IDENTIFIER differs from SSMS silently loses the match, and the
         symptom is "fast in SSMS, slow in the application" all over again.
     THE COST, as plainly as the benefit: the index is maintained SYNCHRONOUSLY, inside every
     transaction that touches a base table. An indexed view with an aggregate over a hot OLTP
     table is a write tax and a contention point, because many writers now update the same
     few aggregate rows.
     THE CHOICE AGAINST 25, taught as a pair rather than as two features:
       INDEXED VIEW   pre-compute the answer. Wins when the query is known and repeated and
                      the base tables are read far more than they are written.
       COLUMNSTORE    compute it fast every time. Wins when the questions vary.
     A reader who can say which of those their workload is has learnt the episode.
